DaemonClient

Every call VeilySocial makes to the VeilKnit daemon goes through this class. It owns the binder connection, the app credential, the session token, and the JSON request envelope, so the rest of the app never touches AIDL directly.

SourceDaemonClient.kt
Protocolversion 3
App idveilknit.veilysocial.profile.v1
Daemon packagecom.example.veilknit_deamon

How a call travels

Nothing here speaks to the network. Each method builds a JSON object, hands it across the binder to the daemon, and unwraps the reply. Whether the daemon then uses a live route, the DHT, or the mailbox is its decision, not the app's.

VeilySocial DaemonClient.rawRequest() builds {protocol_version, request_id, action, session_token, …} │ ▼ AIDL binder IVeilKnitApi.transact(String) : String (blocking, one request per call) VeilKnit daemon api/local.rs dispatches on "action", checks the session token and capability │ ▼ Veilid live route if one exists, otherwise DHT record or mailbox delivery

Threading. transact is a blocking binder call, so every method that reaches it blocks the calling thread. connect handles this internally with Dispatchers.IO, but the ordinary methods below are plain synchronous functions — call them off the main thread yourself or you will get an ANR when the daemon is busy.

Reading the badges

Each method is tagged with what it costs. The first tag says how far the call reaches; the rest name the capability the daemon checks before it runs.

Reach

  • on deviceAnswered from the daemon's own state. Fast, no network traffic, safe to poll.
  • leaves the devicePublishes to or fetches from the network. Slow, rate-limited, and visible to other nodes in some form.
  • unauthenticatedRuns before a session token exists. Only the registration and handshake calls qualify.
  • long-livedOpens a subscription that keeps delivering until you unsubscribe. Returns an id, not a result.

The seven capabilities requested at registration are SendMessages, ReceiveMessages, ManageOwnStorage, ReadOwnStorage, ReadPublicProfiles, SubscribeNetworkStatus and SignAppData. The user approves that whole set once, in the daemon's Applications tab. Adding a capability later means a fresh approval.

Connecting

Binding to the daemon, and the request envelope every other method shares.

suspend fun connect(onStatus: (String) -> Unit)
on deviceleaves the device

The whole startup sequence in one call: bind to the service, make sure an approved credential exists, then exchange it for a session token. Call this once and everything else becomes usable.

The onStatus callback fires when the app is waiting on the person rather than on the machine — currently that is the registration approval step, which reports the request number they need to approve.

onStatus
Receives human-readable progress. Show it; the wait can be minutes on a cold daemon.
throws
IllegalStateException for bind failure, rejected or expired registration, or a changed credential generation.
fun close()
on device

Unbinds from the service and drops the cached interface. Safe to call when never connected.

Two things this does not do. It leaves sessionToken populated, so a later call fails inside the daemon rather than failing fast locally. And it does not cancel open subscriptions — call unsubscribe for each id you hold first, or the daemon keeps streaming into callbacks whose service is gone.

private suspend fun bindApi(): IVeilKnitApi
on device

Binds to com.example.veilknit_deamon.BIND_LOCAL_API with BIND_AUTO_CREATE and suspends until the service connects.

Three failure paths are handled separately, because they need different fixes: a SecurityException means the signature permission was not granted, a false return means the daemon is invisible or absent, and onNullBinding means the service refused this caller.

On a false return the connection is still unbound explicitly, because Android retains a reference even when it reports the bind failed.

private fun diagnoseBindFailure(): String
on device

Works out why the bind failed and returns a message that names the fix. Checks in order: is the daemon package visible at all, does it expose the expected service, and was the signature permission granted.

Package invisibility is the common one on targetSdk 30+ and needs a <queries> entry in the manifest, not a code change.

private fun rawRequest(action: String, authenticated: Boolean = true, block: JSONObject.() -> Unit): JSONObject
on device

The envelope every other method is built on. Stamps the protocol version and a monotonic request id, adds the session token unless told not to, applies your block to fill in the action's own fields, and transacts.

On ok: false it throws with the daemon's own error code and message. On success it returns the result object, or an empty one for actions that return nothing.

action
Must match an action name in the daemon's api/local.rs dispatch.
authenticated
Set false only for registration and handshake calls, which run before a token exists.
block
Receiver lambda on the request object. Put action-specific fields here.

Getting trusted

The daemon does not take the app's word for who it is. Registration establishes a shared secret once, with the person's approval; every launch after that proves possession of it.

private suspend fun ensureCredential(onStatus: (String) -> Unit)
unauthenticatedon device

Returns immediately if a secret and generation number are already stored. Otherwise it generates a 32-byte request token, submits a registration request naming the app and its requested capabilities, and polls every 1.2 seconds until the person decides.

On approval the secret and its generation are written to SharedPreferences under veilysocial_profile_daemon. Rejection and expiry both raise.

Uninstalling the app loses the secret while the daemon keeps its side of the registration. Reinstalling therefore starts a second approval flow rather than resuming the first.

private suspend fun authenticate()
unauthenticatedon device

A challenge–response handshake. begin_authentication returns a challenge id, nonce, validity window, credential generation and the capability list; the app answers with an HMAC over all of it and receives a session token.

The stored generation is compared against the daemon's before the proof is computed. A mismatch means the daemon rotated or revoked the credential, and the only cure is clearing app data and registering again.

private fun computeProof(secret, appId, challengeId, nonce, issuedAt, expiresAt, generation, capabilities): ByteArray
on device

HMAC-SHA256 over a domain-separated, length-prefixed concatenation, in this exact order: the domain string veilknit/app-auth/v2, the app id length as little-endian u32, the app id bytes, then challenge id, issued-at, expires-at and generation as little-endian u64, then the capability count, then each capability's UTF-8 bytes followed by a zero byte.

Byte-exact. The daemon rebuilds this same input and compares. Reordering fields, changing the domain string, or dropping a terminator silently produces a wrong proof and an authentication failure with no clue as to which side is at fault. Change it only alongside the Rust.

Who's out there

Your own identity, the peers the daemon knows, and the pointer that lets other people find your published data.

fun identity(): JSONObject
on device

The logged-in account's identity, including its main DHT key. That key is the durable name for this persona and is what other people's clients use to address you.

fun listAppPeers(): JSONObject
leaves the device

Up to 1000 peers the daemon has seen running this same app id. Passes start_search: true, so calling it also nudges the daemon to look for more rather than only reporting what it already had.

This is discovery's raw input. Being listed here means a node exists and speaks this app's protocol — nothing about whether its profile is real, current, or worth showing.

fun getAppRoot(peerMainDht: String): JSONObject
leaves the device

Looks up the app root record a given peer has published, which is the entry point to their profile data. start_lookup: true means an unknown peer triggers a fetch instead of returning empty.

A successful lookup is what promotes a profile from gossip hearsay to confirmed at source.

fun registerAppRoot(rootDht: String): JSONObject
leaves the device

Publishes your own root record key so other peers' getAppRoot calls can resolve it. This is the moment a profile becomes findable.

fun recommendNodes(nodes: List<String>)
leaves the device

Tells the daemon which nodes this app currently cares about, so its routing work favours them. Capped at 256 nodes, tagged with the context veilysocial_gossip, and expires after 600 seconds.

A hint, not an instruction — the daemon decides what to do with it.

fun setInteractiveActivity(nodes: List<String>)
leaves the device

Declares that someone is actively using the app right now, holding a 90-second lease over up to 256 relevant nodes. The daemon uses this to prioritise responsiveness over battery while the lease lasts.

Renew it while the person is genuinely interacting. Leaving it asserted in the background trades their battery for nothing.

Stored records

App stores are DHT records the daemon owns on your behalf. Each has a fixed number of subkeys, addressed here as numbered locations. Small structured data lives here; anything large belongs in a blob.

fun listStores(): JSONObject
on device

Every store this app has created under the current account, with their ids and record keys. Use it on startup to find stores from a previous session instead of creating duplicates.

fun createStore(name: String, subkeys: Int): JSONObject
leaves the device

Creates a new record with subkeys writable locations and initialises it immediately.

The subkey count is fixed at creation. Growing later means a new record and a new key, which invalidates every pointer anyone else stored. Size for the data's eventual shape, not its first day.

fun readStore(storeId: String, locations: List<Int>, force: Boolean = false): JSONObject
on deviceleaves the device

Reads one or more subkeys of a store you own. Defaults to whatever the daemon has cached, which is why the reach is either — pass force = true to insist on a network round trip.

force
Bypasses the cache. Slower and noisier; use when staleness would be wrong, not by default.
fun writeStore(storeId: String, location: Int, bytes: ByteArray): JSONObject
leaves the device

Writes one subkey, base64-encoded on the wire. The wrapper sends a one-element writes array, though the daemon's action accepts several — batching would be a wrapper change, not a protocol one.

fun readPublicStore(recordKey: String, locations: List<Int>, force: Boolean = true): JSONObject
leaves the device

Reads someone else's record by key. This is how another person's published data is fetched, and it defaults to force = true because a stranger's record is assumed to have moved on since you last looked.

Large payloads

Blobs carry anything too big for a subkey — profile documents, images, widget packages. They are content-addressed, so the same bytes always produce the same hash.

fun uploadBlob(contentType: String, data: ByteArray): JSONObject
leaves the device

The one to use. Opens an upload, sends the data in 256 KiB chunks, and finishes it, returning the blob object with its root record key. If any chunk throws, the upload is aborted before the error propagates, so a failure does not leave a partial upload holding daemon resources.

Identical bytes give an identical hash regardless of who uploads them. Reusing an avatar or a widget across two personas links them permanently. Salt per identity before uploading anything a person authored themselves.

fun downloadBlob(rootRecordKey: String, maxBytes: Int = 4 * 1024 * 1024): Pair<JSONObject, ByteArray>
leaves the device

Reads the blob's metadata first to learn its size, refuses anything over maxBytes, then fetches the whole thing and returns the metadata alongside the decoded bytes.

The size check happens before the data is requested, so an oversized blob costs one small round trip rather than a download.

These bytes came from a stranger. Nothing here validates or sandboxes them. Anything that decodes the result — image decoders especially — is parsing hostile input.

fun beginBlobUpload · appendBlobUpload · finishBlobUpload · abortBlobUpload · deleteBlob · readBlobRange
leaves the device

The pieces uploadBlob and downloadBlob are built from. Reach for them directly only when you need something the convenience wrappers do not do — resuming an interrupted upload, streaming a range without buffering the whole blob, or passing an expected_sha256_hex to have the daemon verify the result.

readBlobRange
Offset and length in bytes. Length 0 returns metadata only, which is how downloadBlob does its size check.
deleteBlob
Removes your local copy. It does not unpublish anything anyone else has already fetched.

Talking to people

Two very different things share this section. Gossip is cheap, unverified and best-effort. The message stream carries delivered application messages, which the daemon has already routed directly or through the mailbox.

fun sendGossip(peerMainDht: String, payload: ByteArray): JSONObject
leaves the deviceSendMessages

Sends a handshake-free datagram over the target's published route. There is no session, no delivery guarantee, and no retry.

The receiver cannot trust any of it. The daemon's own description is explicit: the claimed sender and the payload are unverified hints until confirmed against the app root or the DHT. Treat inbound gossip as a rumour worth checking, never as a fact. VeilySocial keeps payloads under 8 KiB.

fun subscribeMessages(onMessage: (JSONObject) -> Unit, onClosed: (String) -> Unit): Long
long-livedReceiveMessages

Opens the application_messages stream and delivers each event as it arrives. Returns a subscription id for unsubscribe.

Messages reach this stream whichever way the daemon obtained them — a live direct route if the sender had one, or the mailbox if they did not. The app sees delivery, not the route it took.

Callbacks arrive on a binder thread. Marshal to your own scope before touching UI state. Lines that fail to parse are dropped silently, so a malformed event will not crash the stream but also will not tell you it happened.

Open requests

Service requests are the public counterpart to messaging: a request anyone watching for that service id can see and answer, rather than one addressed to a single recipient. This is the primitive for host-and-join interactions.

fun publishServiceRequest(intendedHostMainDht, serviceIdHex, manifestHashHex, instanceIdHex, payload, delegationAllowed = true, spectatorsAllowed = false, ttlSeconds = 900): JSONObject
leaves the deviceSendMessages

Publishes an open request naming an intended host, the service and the exact manifest hash it expects. It stays live for its TTL and then expires on its own.

intendedHostMainDht
Who you would prefer to answer. Not exclusive when delegation is allowed.
manifestHashHex
Pins the exact service definition, so a responder running different code cannot silently answer.
instanceIdHex
Distinguishes this particular session from other requests for the same service.
delegationAllowed
Whether someone other than the intended host may take it. Default true.
spectatorsAllowed
Whether third parties may observe. Default false.
ttlSeconds
Default 900. Expiry is the cleanup mechanism — an unanswered request disappears rather than lingering.
fun withdrawServiceRequest(requestIdHex: String): JSONObject
leaves the device

Retracts a request before its TTL runs out. Use it when the person cancels, so watchers stop offering to answer something nobody wants any more.

fun sendServiceReply(requestIdHex: String, replyRouteBlobBase64: String, payload: ByteArray): JSONObject
leaves the deviceSendMessages

Answers a request over the reply route the requester published with it. The route blob comes from the request event; it is not something you construct.

fun subscribeServiceRequests(serviceIdsHex: List<String>, onRequest, onClosed): Long
long-livedReceiveMessages

Watches for open requests matching any of up to 64 service ids and delivers each as it appears. Returns a subscription id.

Same binder-thread and silent-parse-failure caveats as subscribeMessages. The list is truncated at 64 without warning.

fun unsubscribe(id: Long)
on device

Closes a subscription by id. Errors are swallowed, so it is safe to call on an id that has already been closed or whose binder is gone.

Helpers

fun ByteArray.toHex(): String · fun String.hexToBytes(): ByteArray
on device

File-level extensions used for every hex field on the wire. hexToBytes requires an even length and throws otherwise; neither validates that the characters are hex digits.

Errors

There is one error type and one place it comes from.

Every failure surfaces as IllegalStateException. When the daemon returns ok: false, the message is its own code and text joined as code: message — so invalid_record_key, message_too_large and the rest come through verbatim and are worth matching on rather than paraphrasing.

Locally raised failures use the same type with a plain-English message: not bound, not authenticated, credential generation changed, blob too large. Since there is no distinct type, code that wants to react differently to a bind failure than to a rejected write has to inspect the message — a sealed error hierarchy would be a worthwhile change here.

Not wrapped yet

The daemon's local API exposes considerably more than this class uses. These are available in api/local.rs today and simply have no Kotlin wrapper.
